# Release notes — v0.7.0 object and collection variable types

**Status:** Drafted alongside IMPL-0009. To be shipped as forge v0.7.0
once the downstream forge-registry verification (IMPL-0009 G.5 follow-up)
is filed and `make ci` passes on `main`. **Semver:** minor bump
following the same pre-1.0 minors-for-features cadence as v0.6.0.

**Breaking changes (read first).** Any blueprint that declares
`type = "choice"`, uses the `choices = [...]` attribute, or sets
`validate = "regex"` will fail to load on v0.7. These three forms
are rejected at load time with an error pointing back at the
migration recipe. Blueprints that use only `string` / `bool` /
`int` / `number` and no validation hooks load unchanged (`int`
emits a soft deprecation warning). The mechanical search-and-replace
recipes are in
[docs/MIGRATION.md § Variable type system upgrade (v0.7+)](../MIGRATION.md#variable-type-system-upgrade-v07).

---

## What's new

### Structured variable types

The `type` attribute on `variable` blocks now accepts the full cty
type-expression grammar:

```hcl
variable "git_provider" {
  type = object({
    repo_type   = string
    repo_url    = string
    project_org = string
  })
}

variable "exposed_ports" {
  type    = list(number)
  default = [8080, 9090]
}

variable "build_targets" {
  type = map(string)
  default = {
    linux  = "amd64"
    darwin = "arm64"
  }
}
```

Templates traverse these values natively via HCL2's attribute and
index operators:

```text
${git_provider.repo_url}       # bare-name form
${var.git_provider.repo_url}   # var.X namespace form
${var.exposed_ports[0]}        # list index
${var.build_targets["linux"]}  # map key
%{ for p in exposed_ports ~}${p},%{ endfor ~}
```

Both forms work, both render the same value — pick whichever reads
clearer at the call site. The `var.X` namespace mirrors what
validation conditions and default expressions already see (per
[DESIGN-0006](../design/0006-object-and-collection-variable-types.md)).

### `validation { ... }` blocks

Variables can carry one or more `validation { condition, error_message }`
blocks. Conditions evaluate against the fully resolved variable scope —
including cross-variable references via the `var.X` namespace — and
stack rather than short-circuit, so authors see every constraint
violation in a single pass.

```hcl
variable "license" {
  type    = string
  default = "Apache-2.0"

  validation {
    condition     = contains(["Apache-2.0", "MIT", "BSD-3-Clause"], var.license)
    error_message = "license must be one of Apache-2.0, MIT, BSD-3-Clause."
  }
}

variable "project_name" {
  type     = string
  required = true

  validation {
    condition     = can(regex("^[a-z][a-z0-9-]*$", var.project_name))
    error_message = "project_name must be lowercase letters, digits, and hyphens, starting with a letter."
  }

  validation {
    condition     = length(var.project_name) <= 40
    error_message = "project_name must be 40 characters or fewer."
  }
}
```

Built-in functions usable inside `condition`: `can`, `try`, `regex`,
`contains`, `length`, `lower`, `upper`, `coalesce`.

### `int` deprecation warning

`type = int` is now a deprecated alias for `type = number`. The loader
emits a one-line warning and continues. No file changes are required
to keep working; update at your own pace to clear the warning.

## Breaking changes

The pre-v0.7 string-tag type allow-list and its ad-hoc validation
hooks are removed:

| Removed in v0.7 | Replacement |
|-----------------|-------------|
| `type = "choice"` | `type = string` + `validation { condition = contains(...) }` |
| `choices = [...]` | Inline list inside the `contains(...)` call above |
| `validate = "regex"` | `validation { condition = can(regex(...)) }` |

The loader refuses blueprints that still use these attributes with an
error pointing at the relevant section of `docs/MIGRATION.md`. There
is no in-tool migrator — per [ADR-0002](../adr/0002-forge-does-not-ship-in-tool-migrators.md),
the patterns are mechanical and fit in one search-and-replace.

The full migration walk-through with before/after snippets lives in
[docs/MIGRATION.md § Variable type system upgrade (v0.7+)](../MIGRATION.md#variable-type-system-upgrade-v07).

## Prompt UX caveats

- **Object variables unfold to per-field prompts** in declaration
  order. The dotted prompt label
  (`git_provider.repo_type`, `git_provider.repo_url`, …) preserves the
  source-order of the type expression even though `cty.Object`'s
  attribute map is otherwise unordered.
- **List and map variables cannot be supplied interactively** in v0.7.
  A required `list(T)` or `map(T)` without a value or default aborts
  with a copy-pasteable `.forge-vars.hcl` snippet pointing the user at
  the `--var-file` escape hatch:

  ```text
  Error: variable "exposed_ports" (list of number) is required but
  cannot be supplied interactively.

  Provide it via --var-file:

      # project.forge-vars.hcl
      exposed_ports = [...]

      forge create ... --var-file ./project.forge-vars.hcl
  ```

  Non-required list/map variables without a value flow through silently
  as a typed `cty.NullVal`.
- **The `choice`-style enum prompt is gone.** Re-declared variables
  (`type = string` + validation `contains(...)`) now use the standard
  string prompt; the validation runs after the user submits and any
  failure stacks into the diff-style error list.

## Lockfile compatibility

Structured-typed variables round-trip cleanly through `.forge-lock.hcl`:
the emitter passes `cty.Value` straight to `hclwrite`, and the loader
hand-decodes the `variables { ... }` block back to `cty.Value`. No
schema changes; existing scalar-only lockfiles continue to load
without modification.

If you migrate an in-flight project from `type = "choice"` to
`type = string` + validation, the next `forge sync` rewrites the
lockfile with the new resolved value shape — no manual cleanup needed.

## What didn't change

- **`--var-file` semantics.** Vars files now accept object, list, and
  map literals against the matching declared types. The existing
  rules (repeatable, mutually exclusive with `--set` per invocation,
  strict `.hcl` extension, unknown-keys-are-warnings, `--force`
  required on `sync`) all carry forward verbatim from v0.6.0.
- **`--set` works for scalars and object literals.** A `--set` value
  for an object-typed variable is parsed as an HCL object literal
  (`--set 'git_provider={repo_type="github",...}'`); `--set` against a
  list- or map-typed variable is rejected with the same `--var-file`
  pointer error documented above (the shell-quoting burden makes it
  not worth supporting inline).
- **CLI flag surface.** No new flags. Every IMPL-0009 change lives
  inside the loader, prompt, lockfile, and template paths — invocations
  are unchanged.
- **forge-registry compatibility.** Existing `validation { ... }`
  blocks in `github.com/donaldgifford/forge-registry` blueprints are
  already on the v0.7 shape — the in-repo test fixtures and the
  downstream registry were migrated together under IMPL-0009 B.7,
  so the registry loads cleanly on v0.7 today. The structured-type
  refactor of the Renovate-config blueprint (collapsing four flat
  `git_provider_*` scalars into one `object` variable) is filed as
  the G.5 follow-up — that work is an opt-in expressiveness
  improvement, not a load-time fix.

## Upgrading

1. Update forge: `go install github.com/donaldgifford/forge@v0.7.0`.
2. Run `forge create` or `forge sync` against an existing blueprint.
3. If the loader rejects with `variable type "choice" is no longer
   supported` or `variable attribute "validate" is no longer
   supported`, walk the
   [migration patterns](../MIGRATION.md#variable-type-system-upgrade-v07) —
   the rewrite fits on one screen per variable.
4. If you see `variable type "int" is deprecated`, you can keep
   running or switch to `type = number`; both work.

If you maintain a registry whose blueprints predate v0.7, pin forge to
v0.6.0 in your CI until the registry has been migrated:
`go install github.com/donaldgifford/forge@v0.6.0`.
