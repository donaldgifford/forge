# Release notes — v0.5.0 HCL lockfile cutover + `forge migrate` removed

**Status:** Drafted alongside IMPL-0006 + IMPL-0007. To be shipped as
forge v0.5.0 once the downstream forge-registry verification
(IMPL-0006 C.6) is green and `make ci` passes on `main`.
**Semver:** minor bump per IMPL-0006's release-line decision —
pre-1.0 minors are the right channel for a documented breaking
change. Precedent: v0.3.0 (templates), v0.4.0 (configs). Per
IMPL-0007 OQ-1 the lockfile cutover and the `forge migrate` removal
ship in the same release.

---

## ⚠️ Breaking change

**Existing `.forge-lock.yaml` files will not load.** v0.5.x rejects
bare YAML lockfiles at load time with a rescaffold-or-pin pointer.
Per [ADR-0002](../adr/0002-forge-does-not-ship-in-tool-migrators.md),
**there is no `forge migrate lockfile` command**. You have two
supported paths:

1. **Rescaffold the project (recommended):**

   ```sh
   forge create <blueprint> --output-dir <new-dir>
   # Move / merge new files into your existing project; resolve diffs
   # the same way you would on any forge sync.
   ```

   The new tree contains a fresh `.forge-lock.hcl`. From there
   `forge sync` and `forge check` behave normally.

2. **Pin to the last YAML-lockfile release:**

   ```sh
   go install github.com/donaldgifford/forge@v0.4.1
   ```

   v0.4.1 continues to read and write `.forge-lock.yaml`
   indefinitely. It is also the last release that ships
   `forge migrate` (see the next section).

The full guide is in
[docs/MIGRATION.md](../MIGRATION.md#migrating-lockfiles-from-yaml-to-hcl-v04x--v05x).

## ⚠️ Also breaking: `forge migrate` removed

Per [ADR-0002](../adr/0002-forge-does-not-ship-in-tool-migrators.md)
and [IMPL-0007](../impl/0007-remove-forge-migrate-command.md), the
`forge migrate templates` and `forge migrate config` subcommands —
along with the `internal/migratecmd/` package — are removed from
the main branch in v0.5.0. The v0.4.1 binary continues to ship them
indefinitely; users on v0.2.x or v0.3.x format files follow the
**pin → migrate → upgrade** pattern:

```sh
# Pin the binary that still has `forge migrate`:
go install github.com/donaldgifford/forge@v0.4.1

# Run the migrators against your registry (v0.2.x users: both;
# v0.3.x users: just the config one):
forge migrate templates --path /path/to/registry
forge migrate config    --path /path/to/registry

# Then upgrade to the current release:
go install github.com/donaldgifford/forge@latest
```

The load-time YAML-rejection errors in `internal/config/loader.go`
and `internal/lockfile/lock.go` surface this path inline — per
IMPL-0007 OQ-3 they include the literal `go install` invocation
so the rescue path is one copy-paste away.

The full updated guide (with the new error wordings and the
by-version flowchart) is in
[docs/MIGRATION.md](../MIGRATION.md).

## What changed

Forge's project lockfile (`.forge-lock.yaml`) moved to HCL
(`.forge-lock.hcl`). With templates already on HCL2 (v0.3.0) and
configs on HCL (v0.4.0), the lockfile was the last YAML touchpoint
in a forge-managed project — v0.5.0 closes that gap. The
loader/emitter pair lives in `internal/lockfile/` and uses
`hashicorp/hcl/v2/hcldec` (for eager fields) plus hand-decoding
(for the dynamic `variables` block):

```hcl
# .forge-lock.hcl — generated by forge, do not edit manually
blueprint {
  registry_url = "github.com/donaldgifford/forge-registry"
  name         = "go-api"
  path         = "go/api"
  ref          = "v1.2.0"
  commit       = "a3f9c1d"
}

created_at    = "2026-05-19T10:15:30Z"
last_synced   = "2026-05-19T10:15:30Z"
forge_version = "0.5.0"

variables {
  project_name = "my-api"
  go_module    = "github.com/example/my-api"
  use_grpc     = false
  port         = 8080
}

default ".editorconfig" {
  source   = "registry-default"
  strategy = "overwrite"
  hash     = "sha256:abc123..."
}

managed_file "Makefile" {
  strategy = "merge"
}
```

The rationale is in
[IMPL-0006](../impl/0006-migrate-lockfile-from-yaml-to-hcl.md) and
the design lineage in
[DESIGN-0004](../design/0004-unify-config-file-format-after-hcl2-cutover.md).

## Upgrading

1. **Confirm forge version.** The CLI now requires
   `.forge-lock.hcl`; bare `.forge-lock.yaml` produces the
   rescaffold-or-pin error.
2. **For each forge-scaffolded project you maintain:** pick one
   of the two paths in the breaking-change section above. Most
   projects should rescaffold — it is fast, deterministic, and
   produces an HCL lockfile that matches the current registry
   state.
3. **Verify** with the usual `forge check` and `forge sync`
   workflow:

   ```sh
   forge check          # surfaces drift between project and lockfile
   forge sync           # picks up registry changes; updates lockfile
   ```
4. **Update your CI pinning.** If your build pipeline pins a
   forge version, bump it to v0.5.0 (or pin to v0.4.x explicitly
   while you plan the cutover).

## Behaviour changes worth knowing

- **No `forge migrate lockfile` command exists.** Per ADR-0002,
  forge does not ship in-tool migrators for generated artifacts.
  The lockfile is a generated artifact, not authored content —
  the canonical migration path is to rescaffold or pin.
- **Loader rejects bare `.forge-lock.yaml`.** The error message
  is explicit:
  *"lockfile .forge-lock.yaml: YAML lockfiles are no longer
  supported in this version of forge; either rescaffold this
  project from the current blueprint, or pin forge to v0.4.x
  (see docs/MIGRATION.md)"*.
- **Both formats present? HCL wins.** If both `.forge-lock.hcl`
  and `.forge-lock.yaml` are sitting in the project root, forge
  reads the HCL and ignores the YAML. Delete the stale YAML once
  you've confirmed the HCL is correct.
- **Native typed variables.** HCL carries strings, numbers,
  booleans, lists, and maps natively. The previous YAML format
  encoded everything as a YAML scalar and inferred types on
  read; the HCL format preserves declared types end-to-end.
- **Block-shaped per-file entries.** Where YAML had list-of-objects
  for `defaults`, `managed_files`, the HCL form uses one labelled
  block per entry (`default "<path>" { … }`,
  `managed_file "<path>" { … }`). The label becomes the `Path`
  field on the in-memory struct, matching the convention already
  established for `variable` / `blueprint` blocks in the config
  files.
- **`yaml.v3` dropped from `internal/lockfile/`.** The wider
  `gopkg.in/yaml.v3` module dependency in `go.mod` remains —
  `internal/config/global.go`, `internal/migratecmd/`, and
  `internal/registry/cache.go` still use it. Full removal waits
  on IMPL-0007 (which deletes `internal/migratecmd/` and the
  legacy `forge migrate` subcommands).

## Before you cut

- [ ] Run `make ci` locally — green.
- [ ] Verify `forge create` against the canonical downstream
      registry (`github.com/donaldgifford/forge-registry`) produces
      a `.forge-lock.hcl` that loads cleanly via `forge check` and
      `forge sync`.
- [ ] Verify `forge check` against a project with a frozen
      `.forge-lock.yaml` surfaces the rescaffold/pin error
      (rejection-path coverage already in
      `internal/lockfile/loader_hcl_test.go`
      `TestLoadLockfile_RejectsYAMLOnly`).
- [ ] Tag and push: `git tag v0.5.0 && git push --tags`. The
      goreleaser workflow takes it from there.
